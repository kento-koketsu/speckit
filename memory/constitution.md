# プロジェクト憲章

**プロジェクト名:** マコなり社長の名言・格言ジェネレーター

**憲章バージョン:** 1.0.0

**批准日:** 2025-10-14

**最終改訂日:** 2025-10-14

---

## 目的

本憲章は、マコなり社長の名言・格言ジェネレータープロジェクトの基本原則とガバナンスフレームワークを確立します。すべての開発判断を導く不可侵の基準を定義し、プロジェクトライフサイクル全体を通じて一貫性、品質、保守性を保証します。

本プロジェクトは、マコなり社長の感銘的な名言をランダムに表示するWebベースの名言ジェネレーターを提供します。ボタン操作により名言が表示されます。

---

## 核心原則

### 原則1: ユーザー体験優先

すべての機能は、直感的でレスポンシブなユーザーインタラクションを優先しなければなりません。名言表示と生成メカニズムは以下を満たす必要があります：
- ボタンクリックへの即座の反応（体感レイテンシ100ms未満）
- 読みやすく美的に優れたタイポグラフィでの名言表示
- デスクトップとモバイルデバイスでのシームレスな動作
- すべてのユーザーインタラクションに対する視覚的フィードバック

**根拠:** 核となる価値提案は、感銘的なコンテンツを即座に届けることです。遅延や貧弱な表示は、名言の感情的インパクトを損ないます。

### 原則2: コンテンツの完全性

すべての名言は、本物であり、適切に帰属され、文化的に敬意を払ったものでなければなりません。システムは以下を満たす必要があります：
- 出典検証メタデータ付きで名言を保存
- 帰属を正確に表示
- 誤訳なく日本語の真正性を維持
- 名言コンテンツの改変や破損を防止

**根拠:** プロジェクトの信頼性は、マコなり社長の言葉を正確に表現することに依存します。誤引用や誤帰属は、信頼とブランドの評判を損ないます。

### 原則3: シンプルさと集中

アプリケーションは、単一の明確な目的を維持しなければなりません：ランダム名言生成。新機能は以下を行ってはなりません：
- 核心機能から注意をそらす複雑さの導入
- 広範なユーザー設定やセットアップの要求
- 明確な正当化なしでの依存関係の追加
- ロード時間パフォーマンスの低下

**根拠:** 機能肥大化は、感銘的な名言を得る即座の満足体験を希釈します。最良の設計は、ニーズを満たす最もシンプルなものです。

### 原則4: アクセシビリティと包摂性

アプリケーションは、能力に関係なくすべてのユーザーがアクセス可能でなければなりません。すべてのUI要素は以下を満たす必要があります：
- 最低でもWCAG 2.1レベルAA基準を満たす
- キーボードナビゲーションをサポート
- 適切なARIAラベルとロールを提供
- 十分な色のコントラスト比を維持（最低4.5:1）
- スクリーンリーダーをサポート

**根拠:** 感銘的なコンテンツはすべての人が利用可能であるべきです。アクセシビリティは任意ではなく、倫理的なソフトウェア開発の基本要件です。

### 原則5: パフォーマンスと効率性

アプリケーションは迅速にロードし、効率的に動作しなければなりません。技術要件：
- 初期ページロードは3G接続で2秒未満で完了
- 名言生成は50ms未満で実行
- バンドルサイズは100KB（gzip圧縮後）を超えてはならない
- 不必要な再レンダリングや計算オーバーヘッドがないこと

**根拠:** ユーザーは即座の満足を期待します。遅いパフォーマンスは、迅速な感銘的アクセスの目的に矛盾し、離脱を招きます。

### 原則6: コード品質と保守性

すべてのコードは明確で、文書化され、テスト可能でなければなりません。開発基準：
- すべての関数は明示的な型定義を持つ必要がある
- すべてのパブリックAPIはJSDocコメントを含む必要がある
- ロジックコンポーネントのテストカバレッジは80%以上
- コミット前にリンターチェックに合格する必要がある
- 本番コードにTODOやFIXMEを残さない

**根拠:** 将来の開発者（未来のあなた自身を含む）は、コードを効率的に理解し修正する必要があります。品質実践を省略するプロジェクトでは、技術的負債が急速に蓄積します。

### 原則7: データ主権とプライバシー

アプリケーションは、ユーザーのプライバシーを尊重し、データ収集を最小限に抑えなければなりません。要件：
- 明示的な同意なしで個人データを収集しない
- ユーザーの認識なしでサードパーティトラッキングスクリプトを使用しない
- すべての分析は匿名化される必要がある
- GDPRおよび関連するプライバシー規制に準拠
- ローカルストレージの使用は透明で最小限

**根拠:** ユーザーは私たちに注意を信頼しています。そのインタラクションをデータ収集のために悪用しないことで、その信頼に応えなければなりません。

## ガバナンス

### 改訂手順

1. **提案:** チームメンバーは誰でも `/memory/constitution.md` へのプルリクエストを通じて改訂を提案できる
2. **レビュー:** 改訂は少なくとも1人の他のチームメンバーによってレビューされる必要がある
3. **影響分析:** すべての依存テンプレートとドキュメントを更新する必要がある
4. **バージョンアップ:** 憲章バージョンはセマンティックバージョニング規則に従って増分する必要がある
5. **批准:** 変更はメインブランチへのマージ時に発効する

### バージョニングポリシー

**MAJOR**バージョン (X.0.0): 基本原則の再定義、削除、または過去の決定を無効にするガバナンス変更

**MINOR**バージョン (0.X.0): 新しい原則の追加、既存原則の新要件による実質的な拡張

**PATCH**バージョン (0.0.X): 明確化、誤字修正、意味的変更のない表現改善

### 準拠レビュー

各リリースマイルストーン前に：
- すべての実装は現在の憲章原則に対して監査される必要がある
- すべての逸脱は正当化とともに文書化される必要がある
- 繰り返される逸脱は憲章レビューをトリガーする必要がある

### 権限と拘束力

本憲章はすべての開発決定を拘束します。対立の場合：
1. 憲章原則は機能リクエストよりも優先される
2. 前の原則は後の原則よりも優先される
3. 文脈が要求する場合、原則の精神が文字通りの解釈よりも優先される
4. 解決不可能な対立は憲章改訂のためにエスカレートされる必要がある

本プロジェクトはGitHub Spec-Kit方法論に従います：
1. **Specify（仕様化）** → `/specs/` で要件を定義

すべての仕様、計画、タスク、実装は憲章原則に沿っている必要があります。方法論プロセスが原則と対立する場合、原則が優先されます。
